# Phase 3D: isolated notice verification

This prototype accepts the exact eight-line Japanese notice used in the isolated 002 trial. It checks notice and target folder, target ID and name, source version and modification time before and after reading, and SHA-256 of the target text. It rechecks metadata via a guarded wrapper before the existing 3B relay saves. Notice and target are untrusted: a matching digest establishes content consistency, not author identity, editorial truth, source authorization, or a human decision. It never independently fetches source URLs and cannot authorize READY or publishing.

The read-provider contract here is exact: Google Docs paragraphs joined with LF, no trailing LF. The 3B Drive provider uses Google Docs plain-text export, and its bytes have NOT been proven equivalent to that contract. A real independent Docs adapter with explicit paragraph normalization and authentication must be implemented and tested; do not silently trim or assume export bytes match. Stable metadata checks are not an atomic snapshot across Google Drive and SQLite: a document can change immediately after the last check. Record and review the received version and digest; reject later mismatch. A malicious actor with write access to the folder can replace both content and notice. Restrict folder writers and consider authenticated signatures if the threat model requires producer authentication.

Call initRelay and initNotice before processing. Local notice_attempts logs IDs, status and time only. This is not atomic with candidate storage. If audit storage fails after candidate commit, the call fails and retry uses the existing atomic receipt. A failure while writing an audit record cannot itself be recorded in the same unavailable database. Listing and real notification discovery are not implemented. All E2E is isolated using 2E temporary SQLite; no production D1, scheduled task or remote write.

Independent service-account credentials, a keyless token exchange, and folder-only access are not yet verified. Never commit credentials or borrow the Codex connector. Future unattended delivery requires a trusted producer protocol, Drive/Docs auth, real version-consistent reads, durable state and retries, monitoring, retention/deletion rules, full-state dedupe, and separately approved Operator integration.
