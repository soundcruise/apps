# Phase 3D: isolated notice verification

This prototype accepts the four exact Japanese field/value pairs used in the isolated 002 trial. An empty paragraph may appear between complete pairs; leading/trailing empty paragraphs, empty field values, whitespace-only paragraphs and unknown fields are rejected. Values are never trimmed or normalized. This applies only to the notice: the target body is hashed exactly as received. It checks notice and target folder, target ID and name, source version and modification time before and after reading, and SHA-256 of the target text. It rechecks metadata via a guarded wrapper before the existing 3B relay saves. Notice and target are untrusted: a matching digest establishes content consistency, not author identity, editorial truth, source authorization, or a human decision. It never independently fetches source URLs and cannot authorize READY or publishing.

The read-provider contract here is exact: Google Docs paragraphs joined with LF, no trailing LF. The 3B Drive provider uses Google Docs plain-text export, and its bytes have NOT been proven equivalent to that contract. A real independent Docs adapter with explicit paragraph normalization and authentication must be implemented and tested; do not silently trim or assume export bytes match. Stable metadata checks are not an atomic snapshot across Google Drive and SQLite: a document can change immediately after the last check. Record and review the received version and digest; reject later mismatch. A malicious actor with write access to the folder can replace both content and notice. Restrict folder writers and consider authenticated signatures if the threat model requires producer authentication.

Call initRelay and initNotice before processing. Local notice_attempts logs IDs, status and time only. This is not atomic with candidate storage. If audit storage fails after candidate commit, the call fails and retry uses the existing atomic receipt. A failure while writing an audit record cannot itself be recorded in the same unavailable database. Listing and real notification discovery are not implemented. All E2E is isolated using 2E temporary SQLite; no production D1, scheduled task or remote write.

An isolated October 30 trial used a short-lived service-account token impersonated via the owner's interactive OAuth, read the shared folder and Docs, matched the candidate digest, and delivered one item to local SQLite. One outside-file access returned 404; this does not prove access to every other file is denied. The trial used a temporary adapter, not the checked-in provider. Owner OAuth is not unattended workload identity. Never commit credentials or borrow the Codex connector. Future unattended delivery requires a trusted producer protocol, independent workload identity, a Docs adapter, durable state and retries, monitoring, retention/deletion rules, full-state dedupe, and separately approved Operator integration.
