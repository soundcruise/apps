# Isolated Cloud Run reader boundary

The Operator Dot relay is off by default. Explicit server-side `NEWS_DOT_REVIEW_ENABLED=true` requires `NEWS_DOT_REVIEW_ORIGIN=https://news-dot-review-isolation-607890849010.asia-northeast1.run.app`. Any other value fails closed on Dot routes without impacting other Operator routes. No endpoint, headers or Google credentials are selected by the browser. Relay only forwards the Access assertion, sets redirect=error, bounds response and wait time. The Cloud Run handler independently checks issuer, audience, RS256 signature, expiration, not-before, human identity and the configured Operator email allowlist; keys are fetched from the configured issuer. ADC must use the existing Firestore review-only service account; key files and emulator overrides are refused.

Cloud Run setup for a separately approved isolated experiment: service `news-dot-review-isolation`, project `cruise-news-drive-isolation`, region `asia-northeast1`, 1 vCPU, 512 MiB, min 0, max 1, concurrency 4, timeout 10s, request billing, existing review-reader identity. Set `DOT_FIRESTORE_PROJECT`, `NEWS_ACCESS_ISSUER`, `NEWS_ACCESS_AUD` and `NEWS_OPERATOR_EMAILS` through server-side deployment configuration, separately from the container image. Values must match existing verified Operator settings. Do not copy assertions into logs or files. Observe actual service URL before enabling relay. No public service, IAM, API, or Worker configuration is created by this repository change.

If the Invoker IAM check is disabled and ingress=all, unauthenticated requests reach the container before JWT validation. A stolen bearer assertion can be replayed until expiry. Four in-process admissions and 8-second deadlines mitigate local overload only: they are neither global rate limiting nor a spending cap. Cloud Run can temporarily exceed max instances. For a short isolated experiment use a defined monitoring window, stop thresholds and responsible operator. For ongoing use evaluate external Application Load Balancer + Cloud Armor with direct run.app ingress blocked, or a proven Google workload identity and Invoker IAM; neither is configured or proven here. Budget alerts are not hard caps. Avoid assuming Cloudflare-only rate limits protect the direct run.app endpoint.

On unexpected traffic, validation failure, identity mismatch, Firestore permission changes, or cost anomalies, disable `NEWS_DOT_REVIEW_ENABLED` and block ingress/disable the isolated service endpoint; investigate before restoring. These are future operational steps, not authorization to deploy or change existing production services. Test recovery only under approved scope.

The local preview uses the existing reviewer account and local impersonation, but signs fixture JWTs and routes to an in-process handler. It proves neither an actual Cloudflare Access token nor actual Cloud Run invocation. No production D1 query is made: approved, pending, rejected, system exclusions, discovery, decision ledger and takedowns are unexamined; duplicateStatus remains UNCERTAIN and historyComplete false. No formal facts, decision, READY or write path is created. Access configuration includes issuer, audience, allowed humans and policy session lifetime; retrieve them from authorized configuration, never persist an actual assertion. Session expiry and revocation must be checked on the real Access configuration.

The GET-only API validates requests before querying Firestore, uses bounded reader timeouts, response sizes, cursor and list sizes, and emits only event name, status and duration. No raw token, candidate text, URL, email or credential is emitted. HTTP/platform logs and Cloud Logging settings must also be checked before production. A timeout does not cancel every underlying Google SDK operation; the local admission remains occupied until it finishes.

## Access assertion acquisition gate

The Worker receives `Cf-Access-Jwt-Assertion` from Cloudflare on an Access-authenticated request and verifies it before constructing the relay. The Cloud Run API verifies the same application assertion independently; it does not accept a team/global session as a human application assertion. `test/dot-access-transfer.test.js` exercises the actual environment-configured relay using ephemeral local signing keys, a mocked in-process transport and a separately verified API, and checks that Cookie/Authorization do not pass downstream. These are fixtures, not proof that a Cloudflare-issued assertion was obtained or validated.

The stock `cloudflared access login` flow writes its token to local storage according to its documented implementation; do not use it when token-file storage is prohibited. The existing production Worker cannot be used as a token-extraction endpoint without changing its deployment or exposing an assertion. An authenticated browser session by itself does not prove a usable in-memory bridge exists. Before opening a Cloud Run public ingress, establish and review an authorized in-memory acquisition/relay path that does not log, display or save the actual JWT, verify the actual app audience and human allowlist, and arrange the human login. Never ask the user to paste a JWT or cookie into chat. If this gate cannot be satisfied, do not push the image or create a public endpoint.

Sources: https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/ and https://github.com/cloudflare/cloudflared/blob/master/cmd/cloudflared/access/cmd.go

## Isolated Worker browser route

`src/dot-isolated-worker.js` is a separate read-only Worker entry point, with no D1 or assets binding and no candidate decision routes. Its only routes are GET `/api/dot-capabilities`, `/api/dot-candidates` and candidate detail. After Access is correctly configured for the isolated hostname, a human visits the candidate URL in a browser and signs in normally; Cloudflare supplies the application assertion as a request header. The Worker validates it and forwards it server-to-server to the existing reader. Neither the browser nor logs receive Google credentials or the assertion. The supplied `wrangler.dot-isolated.jsonc` disables workers.dev and preview URLs; it is not a deployment and contains no Access secrets or database binding.

The existing Operator configuration disables preview URLs. A separate hostname is not automatically covered by a hostname-scoped Access application; list/read the actual Access destinations, audience and human policy before any isolated deployment. An account Access-app listing returning zero is not proof that no other Access policy or account exists. If an approved existing policy does not cover the isolated hostname, creating or changing a policy requires separate approval. Use that isolated application's real audience consistently for the Worker and Cloud Run; do not substitute production audience or expose any token. A separate application policy can protect a preview if explicitly configured.

`gcloud run services proxy` adds the caller's Google identity to reach an IAM-private service; it does not create a Cloudflare Access assertion. Thus private proxy GET without the additional app assertion can demonstrate IAM reachability and app authentication rejection, but cannot demonstrate authenticated Firestore reading or browser-to-Cloud Run E2E. A Cloudflare Worker calling an IAM-private Cloud Run still needs a proven Google caller identity; none is configured. The separately approved short public-ingress option makes the application's independent JWT check the primary defense. Test it only within a monitored, bounded window, and restore Invoker IAM/close ingress immediately afterward. Local fixture tests prove neither a real Access token nor a Cloud Run service identity.
