# Isolated Cloud Run reader boundary

This is not deployed or configured in the Operator. The Operator proxy is injected only for isolated tests and does not accept an endpoint from a browser. Before production, explicitly approve and configure an HTTPS endpoint, origin restriction, Access issuer/audience, and the same human email allowlist on both sides. The proxy sends only the verified incoming Access assertion, does not forward cookies or Google credentials, refuses redirects, and bounds response bytes and time. Cloud Run independently verifies RS256, issuer, audience, expiry, not-before, age, human type, subject and allowlisted email; JWKS comes from the configured Access issuer. Its Firestore identity must be the existing DB-scoped read-only reviewer. ADC is used; key files and emulator overrides are rejected.

If Cloud Run's Invoker IAM check is disabled, its URL is reachable directly and application JWT validation is the primary barrier. A stolen bearer assertion could be replayed until expiry; do not log it. Evaluate ingress, request limits and rate limiting, auditing, operator revocation, key rotation and failure response before any deployment. An IAM-protected Cloud Run service would additionally require a trustworthy Google ID token for the Worker. No such workload identity is established here; WIF should not be assumed available. Direct Worker-to-Firestore has the same unresolved identity problem. A private bridge with Cloud Run Invoker and a proven external identity remains preferable if feasible.

The live Firestore preview uses the existing reviewer account and local impersonation, but signs fixture JWTs locally and routes the proxy to an in-process handler. It proves neither a real Cloudflare Access token nor Cloud Run invocation. There is no production D1 query here: approved, pending, rejected, system exclusions, discovery, decision ledger and takedowns are all unexamined; duplicateStatus remains UNCERTAIN and historyComplete false. Formal identity and human decisions are never changed.

The local server supports GET candidate list and detail only. Read failures, invalid configuration and oversize results fail closed. Audit attempt retrieval is capped by the existing adapter; this is not a complete ledger. No write API exists. Cloud Run application logs should contain only bounded status codes and timings, never tokens, raw candidate bodies, or credentials. Set stop and rollback procedures, expiry and access policies, request limits, IAM, deployment resources and cost alerts before real cloud testing.
