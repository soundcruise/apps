# Phase 3B: isolated relay prototype

This module is an offline, dependency-injected receiver, not a Google Drive client, scheduled service, production API, or deployed Worker. `poll(db, provider, folderId)` requires a provider with `list(folderId)`, `metadata(fileId)` and `read(fileId)`. The provider must enforce authentication, complete pagination, bounded reads, and return trusted metadata including folderId, file ID, name, version, createdAt, modifiedAt and boolean `published`. The completion marker is an agreed producer protocol, not Google Docs' public-publishing flag. Its concrete implementation is not established. Never synthesize it for unattended processing. The receiver checks folder, true marker, and matching pre/post version and modification timestamp. These checks are only as trustworthy as the provider. Do not expose this prototype to production.

Each candidate is schema checked by the existing 2E ingest. Candidate and idempotency receipt are committed atomically there. A separate append-only attempt record captures source identifiers, payload digest, status, times, candidate identifiers and bounded error details; it is not atomic with ingest. If the process stops after ingest and before the attempt is recorded, a retry replays the existing receipt and appends an attempt. A logging/storage failure may prevent an attempt being recorded; retries must be monitored. Listing errors propagate and are not recorded as empty success. No external acknowledgement protocol or automatic retry exists.

Drive content is untrusted: candidates keep independent evidence blockers and are never READY, human-approved, or published by this relay. The 2E database enforces temporary `dot2e-*` paths and is not an unattended durable production store. File versions, IDs and idempotency keys are distinct; same key/different content conflicts. File name is never identity. The raw candidate is retained by the existing 2E store, not the complete Drive document or error content. Retry history is a local testing log and needs retention, deletion, privacy and size policies before real data.

The isolated `drive-provider.mjs` uses the official Drive HTTP API, accepts a short-lived token from its caller, paginates listings, and supports JSON/text files and Google Docs exports. It requires a producer-set `appProperties.delivery_state=ready` marker; actual producer support and token access are not established. The adapter is tested with fake HTTP responses only. One separately hand-supplied snapshot from the connected Drive tool used a simulated completion marker, not the adapter. There is no Google credential or OAuth setup in this code. Before unattended implementation, establish a dedicated folder, producer completion protocol, OAuth/service identity and access scope, token refresh/revocation, consistent version semantics, durable state, backoff, observability, deletion handling and least-privilege production authorization. Do not assume Codex's connector credentials can be used by another process or Worker.
