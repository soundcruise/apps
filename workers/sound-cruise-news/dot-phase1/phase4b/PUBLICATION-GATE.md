# Dot publication gate: isolated acceptance and limits

The gate is read-only and deliberately returns HOLD for every Dot admission. The server-side approval path independently blocks Dot receipts, including Yamaha-origin Dot candidates; normal Yamaha assisted entries without a Dot receipt continue through the existing path. A missing additive receipt table is treated as no receipts only because a successful admission cannot exist without migration 0026 and its atomic receipt insert. Other database errors propagate. Dropping the table after admissions is outside that valid migration history and requires incident recovery, not use of this compatibility behavior.

The diagnostic checks the D1 candidate, confirmation hash and age, the current staging revision/digest and delivery key, existing validation, source policy and retained NEWS matching. It never fetches an outside publisher. It cannot prove external evidence remains unchanged, reconstruct expired/orphan histories, or lock Firestore and D1 together. A matching snapshot is not authority to publish. Source freshness, retained history and cross-system races remain explicit blockers. A future implementation must establish a current source-specific, authorized recheck and a defensible final-write concurrency boundary before allowing approval.

No new real source is enabled. The existing Morris permission in NEWS-SOURCE-DECISION-REGISTER.md applies to the recorded narrow listing/detail acquisition, freshness, reuse and attribution terms. It is not a general permission to use the generic manual confirmation workflow. The ZOOM listing policy is an internal bounded source assessment, not evidence of a publisher grant for unrestricted automated acquisition, images or reproduction. A real non-Yamaha candidate cannot pass the generic policy until the exact source, acquisition, facts and rights have verifiable evidence consistent with that policy. Fixture permissions and fictional sources are not real permissions.

Before real-cloud acceptance: review the permission evidence and live source-specific policy; define evidence expiry/recheck without evading robots, budgets or existing fetch rules; close publication-time races and retained-history gaps or explicitly define a safe decision policy; review migrations 0025/0026 and their rollback constraints; test isolated D1 and Access with the feature gates off first. Production migration, deployment, D1/Firestore writes and release each need separately authorized plans. Disabling Dot feature gates and rolling back code do not undo a migration or a committed registration; never discard receipts to recover availability.
