# Phase 4B isolated acceptance

`createIsolatedAcceptance` is a test harness, not an Operator endpoint or production admission service. It creates its own in-memory SQLite database and applies the existing NEWS migrations. It accepts no D1/Firestore client, network fetcher or caller-supplied human identity. The actor is always the literal synthetic fixture human; `confirmed:true` is test input, not proof that any actual human checked anything. Restart loses all state. Never wire this harness to production.

The input has the same `snapshot.input` shape as the retained staging record. Phase 1 schema validation is applied first. Dot's source, date, identity and event are used only to bind and detect conflicts with a separate synthetic human observation. Dot's own `supported`, publisher, policy revision, body verification and recommendation claims never become NEWS evidence. A missing/mismatched source, identity, event or explicit date remains `needs_confirmation`.

The only supported positive path delegates to the existing `prepareAssisted`/`saveAssisted` Yamaha Topics human-observation route and its existing source restrictions, legal permission reference, explicit confirmation, product type, date rules, provenance audit, formal NEWS duplicate predicate and publication validation. It accepts no other source. A `pending` row is a fixture candidate, not an approval or published article. The queue and simulated reject use the existing NEWS Operator services.

A fixture delivery key reserves a canonical payload digest and separate human-input digest. Same key/content is a replay; different content is a conflict. An existing assisted request record allows a reserved receipt to recover after simulated ACK loss. Approved duplicates, existing URLs, retained decisions, discovery and takedown records are never overwritten. The test harness does not establish cross-database atomicity, durable replay, or concurrency safety on real D1/Firestore; none of those services is accessed.

Formal duplicate checking in the underlying NEWS predicate is primarily against approved records; local exact-identity protections also check retained candidate, decision, discovery and takedown records. It is not a complete cross-source rejected/takedown identity match and expired history cannot be reconstructed. Therefore production readiness remains HOLD until independently authenticated human confirmation, durable atomic receipt/registration, full-history semantics, independently verifiable permissions/evidence, real Operator workflow and a separately authorized real-cloud acceptance are designed and verified.
