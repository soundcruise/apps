Production Freeze Runtime — isolated candidate, not deployed

Default-OPEN revision (operations package 0.4.0)
The reviewed candidate now uses production-freeze-control-entry.js: public/default
HTTP is always 404. Only the named FreezeOperatorGateway service entrypoint accepts
signed requests. The previous unconfigured public gateway entry is not selected
by the new preparation compiler. No private HTTPS relay, binding or resource has
been provisioned. A separately approved authenticated HTTPS caller must forward
through this named entrypoint; a user-controlled header is not such authentication.

Production availability is conditional on Control health, even while OPEN.
Admission and pre-mutation Control failures return bounded 503/UNKNOWN; CLOSED
admission returns 423. No untracked/fail-open fallback exists. RPC deadline defaults
to 2000ms per call and is validated before admission; timing out does not cancel
the remote operation. There is no automatic retry. New deployment therefore needs
explicit acceptance of this availability dependency and measured capacity/latency.

If a native Source operation succeeded but only effectEnd acknowledgment was lost,
its original success value is preserved for the legacy handler. A sticky tracking
UNKNOWN blocks freeze certification; the Source operation is never repeated.
Later native or effectBegin failures still produce 503/UNKNOWN. Completion or
background failures after an HTTP response cannot change that response: logs and
the ACTIVE/UNKNOWN ledger are authoritative for tracking, not a successful HTTP
code. Account credential rotation must not be retried merely to repair tracking.

Single plain SELECT statements avoid per-query mutation RPCs while remaining
inside admitted invocation/Promise lifetime tracking. Any non-SELECT, semicolon,
CTE/unknown SQL or mixed batch is treated conservatively as mutation. Business
exceptions without mutation intent can complete with an explicit error outcome;
exceptions after mutation remain UNKNOWN. Completion does not mean business save
success. All mutation start/end and waitUntil tracking remain mandatory.

OPEN ledger bounds
Epoch/state and invocation/state indexes avoid per-request whole-history scans.
Explicit production limits bound invocations, effects, active concurrency and
effects per invocation. Admission reserves its effect budget before Source use;
budget exhaustion rejects before the next native mutation. Existing reservations
keep completion possible after new admission is capped. Historical counters and
reservations survive reopen and are transactionally backfilled from PR79 layout.
Signed CURRENT publishes occupancy/limits/warnings. No record is auto-purged and
UNKNOWN/STARTED is never discarded. Counts are not a physical byte/quota guarantee:
approved storage measurements, retention, warning monitoring and manual rollover
are required before deployment. The controller fails closed at capacity instead
of silently changing namespace or deleting evidence.

Preparation compiler
scripts/studio-operations/freeze-open-plan.mjs is pure and has no credential or
network access. It pins the existing Product profile digest, preserves its D1/R2,
vars, sixteen limiters, compatibility date and Cron, and renders a cross-script
DO binding plus a separate private Control profile. Control has no Source D1/R2
binding, no public routes/workers.dev/preview/Cron, and only the receipt signing
Secret. Its SQLite migration creates a new control namespace, not Source D1 DDL.
Authority roles must have distinct canonical Ed25519 key material, not different
JWK labels. Missing real Source timestamp/namespace, roots/certificate, current
floor, private HTTPS caller or approved capacity/retention keeps profilesReady=false.
Even a complete render is candidateOnly and productionEligible=false; it cannot
grant deployment authority or prove that supplied metadata was actually observed.
OPEN readiness verification is separate from authorization of a CLOSED Backup
window and checks owner/epoch/synthetic/nonce/revision/issuer signature.

Rollback and kill-switch boundary
Signed close is the kill switch; UNKNOWN cannot be cleared by a timer or broad
exception handler. Signed cancel/reopen retain their PR79 conditions. A return to
old v138 must never occur while CLOSING/SEALED or a Backup depends on the barrier.
Even an approved OPEN-only code return requires actual invocation/effect handoff,
fixed original bundle/settings, no Studio schema/claims/activation changes, and
explicit monitoring; subsequent coverage is UNPROVEN until reinstrumented.
No automatic rollback, root adoption or Production operation is included.

Purpose and unchanged boundaries
This candidate wraps the existing studio-production-entry / reconstructed v137
delegate. Studio remains OFF. Existing Wrangler entries, configuration, shared
D1 schema, R2 contents, credentials and scheduled configuration are unchanged.
It adds a control ledger, not another product data store or Backup engine.
Production v138 is NOT currently participating in this ledger.

Admission and drain
Every HTTP request, including GET handlers with activity writes, and every
Scheduled invocation must durably obtain admission before calling the delegate.
The Source is the exact shared D1/R2 physical pair. A single SQLite Durable
Object name is derived from its canonical digest. Synchronous ledger transactions
linearize OPEN -> CLOSING against admission. Existing admitted invocations can
finish. New admissions are rejected with 423. Authentication and the original
Account/Pro/Port/4-app SQL stay in the unchanged delegate.

Before each D1 execution/batch or R2 put/delete, a durable effect STARTED record
is required. CONFIRMED follows a successful response. Errors, lost acknowledgments
and unfinished effects remain ACTIVE/UNKNOWN. waitUntil work is included before
invocation completion. A successful handler response does not clear a swallowed
native D1/R2 error. R2 deletion and D1 mutation are never treated as atomic.
The wrapper exposes only the binding operations used by the fixed delegate;
new delegates or new native mutation APIs require another scope review.

close, seal, reopen, cancel
close: signed operator command, expectedRevision CAS, unique operation/window.
seal: no non-COMPLETE invocation or non-CONFIRMED effect in the epoch; independent
signed proof of old-version/in-flight resolution, partial effects resolution,
all-entry deployment coverage, external SQL/R2 exclusion and manual exclusion.
Explicit external-d1/external-r2/manual start and completion ID sets must match.
An empty registry alone cannot seal. Timers and cron removal cannot seal.
reopen: SEALED plus separately signed verified Archive/copy evidence; advances
the epoch. It never restores Source data or deletes unknown operations.
cancel: CLOSING only, all drain complete and signed evidence that Backup/readers
are stopped; allows explicit abandonment without inventing an Archive receipt.
UNKNOWN or in-flight state blocks both seal and cancel. No automatic recovery,
replay, rollback, reopen or retry is implemented. Same command ID+body can be
read back; a different body with that ID is rejected.

CURRENT and the existing PR77 runner
The receipt key signs a fresh nonce, Source, state, window hash and revision.
CURRENT lives at most 30 seconds and cannot outlive its closed window. The client
requires the approved issuer pin and minimumRevision. Each readWindow challenges
the live coordinator; returned immutable receipts feed PR77 verifiedCutlineProvider
and the existing bounded encrypted Backup core. Cached CLOSED windows do not
remain current after reopen. A crash/reopen keeps ledger state.

The operator gateway is a separate, unconfigured entry. It accepts only signed,
bounded POST /control or /current. freeze-client.mjs requires an explicit HTTPS
origin, signing handle, no redirects and no retries. Before Production use it
needs an approved private route/authenticated transport and observed readback.
No gateway route, workers.dev, preview, Cron or Cloudflare resource is created
by these files.

Physical deployment and authority prerequisites — currently HOLD
The Source digest/name is enforced inside the coordinator as well as its caller.
The signed deployment certificate binds namespace ID, Source digest, fixed worker
artifact hash, derived object name and SYNC_DB/SYNC_ASSETS binding names.
JavaScript bindings do NOT expose their physical Cloudflare IDs. An independent
issuer must compare actual Account/D1/R2/DO namespace/deployment metadata before
signing. Correct strings without that observation are not physical proof.

Every entry capable of mutating the shared pair must use that same physical
namespace and object, not another namespace with the same object name. Old v138,
v137, Version/override/service paths and pre-instrumentation work require separate
effective exclusion/resolution evidence. External SQL, R2 clients and manual
management need named exclusion custodians and verifiable completion records;
the code cannot make a custodian assertion true. No legacy operation is inferred
from an empty ledger, fixed wait or current 100% deployment.

Production adoption needs separate explicit approval for:
- the SQLite DO namespace/binding and its costs, unconfigured entry bundles,
  exact resource mapping, private operator gateway and controlled rollout;
- separate operator / external-attestation / receipt key custody, Secret entries
  and approved public roots (no real keys were generated in these tests);
- authoritative external observers, old-version exclusion and initial handover;
- current Host grant, Source S3 read capability, fresh Restore resources/privacy;
- actual freeze, Source reads for Backup and real-data Restore.
Do not deploy these files by merely turning on a flag or reusing test keys.

Trust limits, retention and failure handling
Live signatures/nonces defend network replay; they do not defeat an authorized
Cloudflare administrator, issuer compromise or DO PITR/namespace replacement.
An independently approved durable revision/window floor and control custody are
required. No independent pin service or root was modified in this candidate.
The ledger retains historical invocation/effect/command rows. Configured limits
now bound admission and effects as described above. Storage/latency/retention and
budget approval remain deployment prerequisites. No automatic purge or silent
Source fallback is permitted. A capacity/transport failure affects availability.

Backup freeze and Studio release stages
v138 OFF continuation, additive studio_0001_rc5 DDL, a consistent shared D1/R2
Backup freeze, and Owner canary are separate approvals and safety conditions.
This control ledger does not require shared migrations 0034-0037. Additive DDL
still needs its own schema/journal serialization and Backup/Restore policy.
To shorten user interruption, Source may be explicitly reopened after sealed
Archive/copy verification and a valid reopen receipt; isolated Restore can then
continue from the sealed Archive. An unknown result never authorizes reopening.
Never restore the whole live Source to undo a later Account B/other-owner update.
