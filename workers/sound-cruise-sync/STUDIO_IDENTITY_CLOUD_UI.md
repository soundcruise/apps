# Studio Identity / Cloud UI candidate

PR #55 is the direct dependency. Studio 0.49.0, Project schema 2. The existing Account/Pro Owners, P-256 device session, D1 transactions, Project repository/Web Locks/CAS and IndexedDB outbox remain authoritative. No shared Account/Pro implementation or legacy writer is changed.

## Entry and trust

`mountStudioIdentityHost` is explicit host composition for isolated acceptance. It mounts ordinary-user fields/actions in the Studio Home panel using the existing Session adapter and Client. Normal boot still mounts only the display panel. Loading the existing Account core and Pro-device-session scripts is inert; it does not create a session, initiate a request or activate Cloud.

`studio-transport.mjs` accepts exact document paths and native Pro/recovery paths. Both consumers require a branded factory transport. Isolated destinations are reserved `.invalid` HTTPS or loopback HTTP. The exact known Production origin and `/v2/studio/document` can be represented as a **candidate**, but every actual candidate request throws `production-release-not-authorized` before calling fetch. There is no query/localStorage release flag. A separately approved future deployment must connect the transport; current tests are not production reachability evidence. Credentials are omitted, redirects are errors, cache is disabled; destination userinfo/query/fragment and other origins/paths are refused. This does not protect against a privileged same-origin script replacing the trusted fetch implementation or directly calling another API.

The real server candidate factory maps the public document path into the existing Owner. D1 OFF/canary/general remains the sole server authority. Existing Account/Pro final SQL guards and schema inspection are unchanged. Production entrypoint/Wrangler are not connected. Browser Origin is subject to existing backend exact Origin allowlists; no ambient cookies or client activation claim authorizes a save.

## User flow

The host provides native Pro verification/renewal, Studio-only registration with no app memberships, enrollment of an existing Account, additional Device kit and Studio-only revoke/list, explicit disconnect/Account switch, native Account recovery and recovery-commit ACK reconciliation. Recovery kit preparation and explicit user storage confirmation precede registration/recovery. Kits are shown only in a sensitive textarea for user-managed custody. Private P-256 keys use the existing nonextractable IndexedDB store; no new authentication engine is added. Account/Pro credentials and recovery material remain in host/Session memory and user-controlled kit UI, never in outbox/receipt/logs. Reload requires explicit reconnection from safely retained material; pending document content survives in outbox. Recovery ACK resume can accept the exact user-held continuation kit and resubmit the same native commit, without making a fresh claim automatically. Registration ACK uses explicit identity-history reconciliation while the prepared request remains in memory; a reload can reconnect with the prepared Account credential if registration committed. No success is inferred when identity is unknown.

The Cloud panel supports local-versus-Cloud save, observe, explicit import, offline/reconnect, CAS conflict, local draft fork, pending Owner adoption, UNKNOWN reconcile, confirmed Cloud-only tombstone deletion and retired unproven draft preservation. A Cloud response never silently overwrites the current local Project. Import is explicit and uses existing repository CAS; a dirty current editor is refused. Synced Cloud deletion preserves local content. UI Cloud OFF retains local/outbox and stops Client use; ON requires native reauthorization. Device revoke affects Studio enrollment, not shared native Account credential deletion.

Capacity inventory shows document count, logical head bytes, stored chunk bytes, active operations, metadata rows/bytes and local UNKNOWN/recovery count. Counts are observations, not an entitlement. Account and Session identity are bound to the displayed compaction epoch/revision. Identity changes clear the old approval. Compaction remains explicit, final-CAS protected and refuses unresolved proof/adoption/UNKNOWN or live erase intents. Canary prohibits Account-wide maintenance. Finite retained heads/tombstones/devices and unresolved evidence can still exhaust the cap; no claim of unlimited service is made.

A CAS-conflicted operation may be explicitly discarded only after fresh Owner reconciliation, exact binding and confirmation. The existing Owner rejects a committed/current head, mismatched digest, adoption dependencies or missing native proof. A durable discard request is stored before send; ACK loss becomes `DISCARD_UNKNOWN`. Send/adopt cannot reuse the original save. Explicit reconcile first reads Owner state: it strictly validates a terminal discard, accepts a real historical commit, or preserves `history-retired` as unproven after peer compaction. Only a still-pending operation with the same current binding may replay its exact discard request. An Owner change with an unresolved discard remains HOLD; there is no automatic new-generation retry. Local draft is retained. Necessary UNKNOWN is not deleted to recover quota.

## Acceptance and remaining gates

The new UI test uses disposable Chrome profiles, actual workerd/D1 and real native Account/Pro routes; only passcode, Turnstile result, limiters and data are synthetic. No production network/real credentials are used.
