# 統合譜面制作 最終UX契約照合と静的モック制作の準備

## 結論

**Astra の契約全文と、私の前回 UX レビューのあいだに、構造的な矛盾はありませんでした。**
- ただし前回の私の案には、Astra の原則（データ喪失・誤った音高・未確定を確定扱い・権限の混同）に触れる箇所が5つあったので、修正しました。主な3点は次のとおりです。
  - 音価の「仮」を薄い色だけで示す案
  - 要確認のTABに、おすすめ案のフレット番号を出す案
  - キー・カポ変更の画面に、手動フォームを一括で置き換えるチェックを置く案
- さらに、契約が正しいほど使い勝手で困る点が2つ見つかりました。
  - コード欄を空けた小節（「前のコードのまま」のつもり）が、TABではすべて要確認になる。
  - カポがあるとき、コード名を「押さえ方」と「実音」のどちらで表示するか。
- どちらも契約は変えずに、UIの決め事として解決策を示します。

**静的モックの制作は、24画面と下記の受入条件で開始してよいと判断します。**

区分の意味:
- 【現行事実】現在のリポジトリで確認したこと
- 【確定】今回確定する UX 契約
- 【暫定】モックで比べてから決めること
- 【未決】ユーザーまたは Astra の判断が必要なこと

## 4. 修正が必要な UX 判断（修正後の案）

1. **仮の音価の表示**（a の修正）【確定】
   - 色は通常の濃さのままにします。
   - 自動で割り当てた音価を含む小節には、**五線の上に細い括弧線と「自動」の文字**を付けます。システムごとに1本にまとめ、色に頼らない形の印にします。
   - 段の見出しは「メロディ　音の長さ：自動を含む」とします。
   - この印は、その小節を確認するまで消えません（契約どおり）。
2. **要確認の TAB の表示**（b の修正）【確定】
   - 該当するイベントの位置に、点線の枠で「押さえ方を確認 Dm」と文字で示します。**フレット番号は表示しません。**
   - 前に固定したフォームとおすすめ案は、パネルの中でだけ並べて見せます。見るだけなら履歴には入れず、採用は明示操作にします。
   - 印刷（確認用）でも、枠と文字はそのまま出します。
3. **キー・カポ変更後の固定フォーム**（c の修正）【確定】
   - 移調・カポ変更の操作そのものは、曲の内容と状態の変更だけで履歴1件にします。
   - 変更前の画面には、「固定した押さえ方3か所が要確認になります」と件数を出すだけにします。
   - 変更した後、状態行の［順に見る］から**別の操作**として「同じ形の候補を確認」を開きます。候補ごとに採用するか、「表示中の候補をすべて採用」（別の履歴1件）を選べます。
4. **空欄のコード**（契約§16の UX 対応）【確定】
   - 契約では、空欄は「未指定」で、前のコードを自動では引き継ぎません。そのまま実装すると、一般的なコード譜（空欄＝前のコードのまま）では TAB の多くの箇所が要確認になります。
   - 対策として、最初に空欄による要確認が出たときに、状態行で一度だけ尋ねます。

     「この曲では、空欄の小節を『前のコードを続ける』として扱いますか？［続ける］［あとで］」

   - ［続ける］を選ぶと、曲の規則として明示的に保存します（契約の「ユーザーが選ぶ曲の規則」）。
   - 「N.C.」はルーペのコード欄から明示的に入力できるようにします。
5. **カポがあるときのコード名の基準**【確定】
   - コード名を入力する欄と表示には、**今の基準（例:「押さえ方・Capo 2」または「実音」）を必ず添えます**。
   - 入力された文字は表示中の基準で解釈し、保存するのは実音です（契約§9）。カポがあるときは、確定する前に「実音 D」を併記します。
   - 基準を曖昧にすると、音の高さを誤ります。
   - どちらの基準を既定にするかは【未決 U3】です。

## 5. 確定 UX 契約

**A. 譜面スタイルの名前と段**

| スタイル | 段（上から） | 既定 |
|---|---|---|
| コード譜 | コード／ストローク／歌詞／ドレミ | 新規作成時の既定 |
| メロディ譜 | コード／メロディ五線（歌詞はその下）／ドレミ（任意） | — |
| ギター譜 | コード／ストローク／ギターTAB（歌詞は任意で小さく） | — |
| 弾き語り譜 | コード／ストローク（任意）／メロディ五線＋歌詞／ギターTAB | — |
| カスタム | 上記の段のオン・オフ＋ギター伴奏五線 | — |

- 画面での呼び名は「譜面」に統一します。内部のワークスペース ID は変えません。
- 段の頭のラベルは「メロディ」「ギター伴奏」「TAB」です。カポがあるときは、TAB の頭に「Capo 2」を表示します。

**1. 単一の Project・Session・Undo**
- フォーム・リズム・音価・一括適用・移調は、それぞれ履歴1件にします。
- パネル内で候補を見るだけの操作、ズーム、選択は履歴に入れません。
- 戻した直後に、状態行で「戻しました：3小節目 C の押さえ方」と表示します。

**G. フォームとリズムの適用範囲**
- フォームの既定は「このコードイベントだけ」です。パネルの見出しを「3小節目・2拍目の C」のように、対象のイベントで表記します。
- 一括適用は「同じコードにも適用（ほか3か所）」です。
  - 判定は root・quality・bass・楽器条件で行います。
  - **固定済みの箇所は対象外として件数を別に表示**し、［固定済みも変更］は別の明示操作にします。
- リズムの適用先は「この小節／曲の基本」で、パネルを開いた場所によって既定が変わります。

**7. Rhythm の記号**
- それぞれに別の記号を割り当てます。

| 意味 | 記号 |
|---|---|
| ダウン／アップ（新しく音を出す） | ↓／↑ |
| 空振り | (↓) |
| 休み | ・ |
| 前の音を伸ばす（持続） | 〜 |
| 消音（止める） | ×止 |
| 音程のない打撃 | × |

- 継承中の小節には、その小節で実際に弾くパターンを表示し、「曲の基本」と文字を添えます。
- 直前の音がない「伸ばす」は、要確認にします（勝手に hit や rest へ変えません）。

**8. 音高・キー・カポの操作**
- 曲情報の行から「何を変えますか？」で目的を選びます。
  1. 歌いやすい高さにする（移調）
  2. 押さえやすくする（実音を保つカポ）
  3. カポで上げる（押さえ方を保つ＝曲全体を移調）
  4. 表記だけ直す（詳細の中）
- どの目的でも、**変更前後のコード列と、メロディの例を1つ**見せます。例:
  - 実音を保つ場合「C G Am F → B♭ F Gm E♭（Capo 2）。歌は C4 のまま」
  - 押さえ方を保つ場合「歌も C4 → D4 へ上がります」
- 固定フォームのうち要確認になる件数を見せます。押さえられなくなる低い音がある場合は、「低いミの音は Capo 2 では出せません」と示します。

**9. 仮の音価**
- 小節単位の印（§4-1）と、段の見出しに表示します。音符1つずつに警告は出しません。
- ルーペで音価を編集するか、［この小節の長さを確認］を押すと、印が消えます。

**10. 出力ごとの状態**
- 紙面の上（画面のみ）に、次の1行を出します。

  「メロディ ✓ ／ ギター伴奏 — ／ TAB 確認2か所 ›」

- 状態は「生成可能／要確認／生成不可」です。生成不可は、その段の場所に理由を1行で書きます。空白にはしません。

**E / 11. 完成譜と確認用の印刷**
- 印刷する段がすべて「生成可能」で、未確認が0のときだけ「印刷」にします。
- それ以外は「確認用として印刷」にします。
  - 各ページのヘッダーに「確認用（未確認の箇所を含みます）」と入れます。
  - 印・枠をそのまま出し、ページ末に脚注を付けます。
  - 透かし文字は使いません。
- 「TABを除いて印刷」も、その場で選べるようにします。

**F / 12. ルーペの DOM の持ち方と IME の保護**
- ルーペ本体は紙面の DOM の外に置き、重ねて表示する層にします。紙面の側は、選択中のシステムの下に**ルーペと同じ高さの空き**を描くだけにします。
- 紙面を描き直したり小節を移ったりしても、入力欄の要素は作り直さず、値だけを入れ替えます。
- 小節やシステムを移るときは、選択中のシステムが画面上の同じ高さに来るようにスクロールを補正します。
- この空きは印刷にもページ割りにも含めません。画面上のページ枠だけが、空きの分だけ高くなります。

**13. 紙面と印刷で共通のレイアウト**
- 1システムの小節数、改ページの位置、段の順番を、画面と印刷で同じ計算から決めます。
- ズームは表示の倍率だけで、改ページは変えません。

**14. Standard と Pro の境界**
- 本棚、マイリズム、高度な CAGED、手での押さえ方編集は、モックでは「準備中」の入口だけを置きます。
- Chord の URL や edition 表示から、Pro の権利を推測しません。
- 本棚から取り込んで、元が削除された素材は、「本棚から（元は削除済み）」と表示して使い続けられるようにします。

**6. 歌詞と音符の対応**
- 対応がまだ確定していない歌詞は、音符ではなく時間の位置に置きます。
- 伸ばし線（メリスマ）やハイフンは描きません。

**入口**
- コード名をクリック → ルーペのコード欄
- 名前付きの「押さえ方」ボタン、または TAB の該当箇所 → フォームパネル
- ストロークの段 → リズムパネル
- 五線の音符 → ルーペのドレミ欄
- 曲情報の行 → キー・カポ・BPM・拍子

## 6. 暫定 UX 契約（モックで比べて決めるもの）

**B. 1システムの小節数と密度の制御**
- 全段で必要な幅を合計し、それが収まる最大の小節数を「4 → 3 → 2 → 1」の順で選びます。
- 画面で守る最小の文字サイズ（100%表示）は、歌詞11px、TABの数字10pxです。印刷では歌詞9pt、TABの数字8ptです。
- モックでは、標準を4小節にした場合と2小節にした場合を比べます。
- 文字を縮めたり、一枚に収めるために縮小したりはしません。

**H. 狭い画面での配置**（既存の境界に従う）

| 幅 | 配置 |
|---|---|
| 1280px以上 | Inspector を常設（320〜360px）。1280px のときは紙面を約94%に縮小 |
| 1279〜801px | Inspector を重ねて表示 |

**その他**

## 9. 静的モックの受入条件

1. 24画面すべてがそろっていること。白黒で表示しても、全ての状態が文字・記号・線の形で区別できること。
2. コード名の編集と押さえ方の選択が、見た目でも、キーボードの名前（アクセシブル名）でも別物であること。
3. フォーム・リズムのパネルの見出しで、適用先（イベント・小節・曲）が読めること。一括適用では、件数と除外する件数を表示すること。
4. 要確認の TAB に、推測したフレット番号が1つもないこと。固定の印と要確認の印が同時に見えること。
5. 仮の音価の印が音符ごとではなく、確認するまで残ること。
6. キー・カポの4つの目的それぞれに、変更前後のコード列・メロディの例・影響件数があること。
7. ルーペが選択中のシステムとその全段を隠さないこと。小節を移っても、ルーペの画面上の位置がずれないこと（2フレームで示す）。
8. 画面のページ枠と印刷プレビューで、1システムの小節数と改ページの位置が一致すること。
9. 確認用の印刷で、未完成の部分が空白になっていないこと。
10. 最小の文字サイズ（§6-B）を下回らないこと。長い歌詞を切り詰めないこと。
11. Toolbar のまとまりは5つを目安にすること。ただし、出力メニューから全機能に届くことを優先する。
12. **利用者による確認**: 初心者3人のうち2人以上が、説明なしで次を行えること。
    - フロー A（新規 → コード → ドレミ → メロディ確認）
    - フロー E（8分 → 16分）
    - S16 で、変更後の結果を正しく予測すること
13. モックは製品のコードとデータに接続しないこと（静的な資料だけ）。

## 10. 技術実装に入る前の停止条件

次のどれかに当たる場合は、実装を始めません。
- 受入条件の 2、3、6、12 のいずれかが満たせない。
- 試作の段階で、紙面の描き直しや小節の移動の後も、IME・カーソル位置・フォーカスが保たれることを確認できない。この場合は、紙面の外の固定編集領域へ切り替えて再審査する。
- 出力ごとの部分表示に必要な、「全体が壊れている」と「声部ごとに未解決」を分けた次版の判定設計（Core v2）ができていない。現行 Core v1 の `ok:false` を無視して描画することは禁止。
- UX 案のどこかに、推測したフレット番号の表示、前のコードを暗黙に引き継ぐこと、固定フォームの自動置換、色だけによる状態表示のいずれかが残っている。
- schema 2 ができる前に、フォーム・リズム・確認状態を「保存済み」に見せる必要が出た。
- 一括操作の前に、履歴の上限（100件・8MiB）を超えないかを事前に確認できない。
- U3（コード名の基準）が決まっていない。
- Pro の範囲（U7）が決まっていない状態で、該当する機能を公開しようとしている。
