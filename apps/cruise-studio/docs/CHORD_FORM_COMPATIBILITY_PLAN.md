# コードフォーム保存の互換設計案（利用者確認待ち）

2026-11-12。表示変更は0.105.0-dev.1。以下の保存拡張は**未実装**。

## 確認済みのUI方針

- ▼は、選択中のマスのフォームとダイアトニックを横並びにする。フォームは指指定を含むコードクルーズ原本の横向き指板を使う。拍位置や未登録の補足文は図の下へ出さない。
- ダイアトニックは譜面のORGキーで開く。別キーの試行はProjectのキーを変更しない。
- 「コードクルーズ」から、上段の図とダイアトニックを維持したまま、その下へ元のExplore指板・任意コード・CAGED選択を展開する。
- コード名はダイアトニック・任意コードの入力確定・取込済み本棚リストからの選択で、既存Session経路を使って直接入力する。別の入力確定ボタンは置かない。1回のUndoで戻す。これと、以下のフォーム素材の保存拡張は別の変更である。
- 配色はStudioのテーマに従う。コードクルーズ本体の設定や保存には接続しない。
- 自動登録の初期楽器条件は標準6弦・22F。ただし、既存の確定済み楽器条件は上書きしない。

## 実装前に確認する保存方針

### 1. 旧データをそのまま読める形で追加する

現行schema2の `studio-chord-form-v1` 素材、`fixed` binding、確認条件は維持する。旧素材・旧bindingの自動変換や起動時の一括登録をしない。

新しいコード入力または明示的なフォーム変更だけに新版素材を作る。提案する識別子は `studio-chord-form-v2`。スナップショットは既存と同じ6弦の押弦／ミュート、カポ、チューニング、物理フレット上限、運指・バレーを基礎にし、由来を「おすすめ／手動編集／本棚取込み」で区別する。本棚由来は元のコードIDを保持し、認証・Sync情報は含めない。手動や本棚のフォームをおすすめ由来と偽らない。

bindingに `auto`／`fixed` を追加して意図を区別する。旧 `fixed` は固定のまま。再生可能かどうかは従来どおり、音・使用弦・楽器条件・確認basisの評価で決め、表示できるだけで確認済みにはしない。新版を理解しない旧クライアントは読込みを安全に拒否する。新版を旧版に黙って変換・切捨てしない。

### 2. おすすめの自動登録

新規Projectは標準6弦 `[64,59,55,50,45,40]`・22Fを初期条件にする。既存Projectに確定済みの別条件があれば保持する。既存Projectの条件が未確認なら、最初の自動登録前に初期条件を適用する旨を画面で確認し、キャンセルできるようにする。

コード名とおすすめ素材・bindingを**同じSession操作とUndo単位**で入力する。`getCommonForm` →既存adapterの検証を通し、Cは既存ロジックが選ぶローコードから始める。コードの実音／カポ相対の既存契約を維持する。おすすめの変更や更新は既存の固定フォームへ遡及させない。

未対応のコード品質・スラッシュベース・不完全フォームはコード名だけを入力し、「フォーム未確定」を表示する。類似した別コードの形で代用しない。自動登録の素材生成に失敗しても、半分だけのbindingや不正素材を残さない。

### 3. 名前変更とフォーム編集

`auto` のコード名変更は新しいおすすめへ更新する。手動／本棚を採用した時点で `fixed` にする。固定後に名前や楽器条件が変わったら、元の形を保持して要確認にし、黙って別の形へ置換しない。

フォーム編集は一時プレビューと「このマスに採用」を分ける。弦ごとの未確定・ミュート・押弦・開放を区別する。素材は追記のみで、複数コードが参照する旧素材を直接編集しない。採用時に安定したProject／bar／chord ID、Session世代、snapshot版、Repository revisionを再検証する。

名前の構成音とフォームの音が不一致、未確定弦あり、演奏条件未確認の場合はその理由を示す。確認済み演奏フォームとして扱わない。元のメロディ音価、ストロークの未入力／休符／伸ばし、Music Modelの基本構造は変更しない。

### 4. 本棚JSON

コード名専用 `sound-cruise/chord-names` version 1は変更せず、引き続き利用できる。フォーム付きは別format／versionを定義する。コード名・元ID・フォルダ情報・必要最小限の6弦フォームと楽器条件だけを厳格に検証して読み込む。

本棚の保存形式で欠けている楽器条件・ミュートを勝手に補完せず、フォーム採用前に確認する。ファイルの読込みだけではProjectへ書かない。現在は一覧のコード選択で名前を直接入力する。将来のフォーム付き転送でも「名前だけ入力」「名前とフォームを採用」を明示的に区別し、後者も1回のUndoで戻す。本棚への書戻し・自動同期はしない。

既存の読取り専用書出し補助を拡張する。通常認証後に利用者が選んだレコードだけを取得し、全localStorageの走査や認証情報の読出しをしない。実本棚は自動試験のデータに使わない。

## 受入試験

- 旧v1 Projectの読込み・保存・JSON往復で既存素材とbindingが不変。
- C等の新規入力→フォーム自動登録→Undo／Redo→CAS保存→再読込→JSON往復。
- 名前変更時のauto更新／fixed保持、共有素材の不変、楽器条件変更時の要確認。
- 手動・本棚由来を正しく保持し、構成音不一致・不完全・未対応品質を確認済みにしない。
- 失敗・競合・UNKNOWN・IME未確定・別Projectへの遅延適用で元のdraftを保護。
- 名称JSON v1の互換、不正／巨大／重複ID／未対応版の拒否、フォームJSONの往復。
- Chrome／WebKitの基本・詳細・右窓・2小節・狭幅、外部／本番バックエンド通信0件。

本番認証・Coming soon・Cloud・公開パッケージ・mainは変更しない。保存契約の実装は、この案の確認後に独立した変更単位で進める。

## 利用者が判断する点

1. **名前変更時の動作**：自動フォームは新しい名前に合わせて更新し、手動／本棚から固定した形は保持して不一致なら要確認にする。この方式を推奨する。
2. **旧版との互換性**：旧Projectは新しい開発版で開ける。一方、新版フォームを登録したProjectは、未対応の古いアプリでは開けない。元データを切り捨てる互換書出しは行わない。変更前のJSONを利用者が残せるよう案内し、旧版読込み拒否も試験する方針を推奨する。
3. **既存Projectの楽器条件**：新規Projectを標準6弦・22Fにする方針は選択済み。既存Projectの別の確定条件は保持し、不明なものに初めて自動登録するときだけ、初期条件を適用する確認を出す方式を推奨する。楽器条件はProject全体に作用するため、既存の確認状態への影響を黙って確定しない。

この3点を含めた保存拡張の実装は、利用者の確認待ち。今回の表示・直接コード名入力の変更だけでは旧Projectの形式は変わらない。
