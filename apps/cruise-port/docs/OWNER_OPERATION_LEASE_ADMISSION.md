## Scope and owners

Only explicit BPM saves on a PR21 reauthorized, readonly/fenced generation are modeled. Existing Account HMAC (`sca1`), canonical Account revision/full manifest, app-device HMAC, Pro entitlement, backend writer fence, Account credential lifecycle and durable SQL clock are reused. The five-second observation reader, UI generation, old reauthorization receipt and dataset historical receipt are never current save credentials. No new authentication service, data authority or Sync engine is installed.

`createIsolatedOwnerOperation` requires a branded test Authority scope, the same IndexedDB factory, existing Account source, Web Locks, existing Shared immutable backup owner and loopback/fixture transport. It is absent from product boot. SQL methods/routes require `fixtureOnly` and `enableOperationLease`, default OFF; product routers, Wrangler, production migrations, deployment bindings and Account lifecycle tables are unchanged. The column/table installer lives in tests only. In lease-enabled fixture mode, the legacy unleased `prepare` / `save` mutation path is rejected; its default-OFF legacy behavior remains unchanged. This is a mode-local contract, not a claim that arbitrary independently configured legacy/raw writers are fenced.

## Exact operation and owner token

`prepare({generation,reauthorizationOperationId,operationId,bpm,expectedBackendRevision,explicit:true})` pins the current full Account/source revision and manifest, PR21 typed generation birth, Control/fence epochs, full Authority pointer/head/key revision, exact dataset/op UUID/request digest/CAS and existing local prepared fingerprint. Only BPM changes; all other fields retain normal Port validation. A pending pin is written and read back **before** any lease request. Existing renewal/adoption/reauthorization pins are retained. Prior operation pins count as resolved only with exact typed backend AND local receipts. Unknown, malformed, aliased or orphan pins stop preparation; immutable pins are never pruned. Adding our own pin requires an exact inventory delta, never adopting concurrent unknown pins as baseline.

The owner token purpose is `owner-operation-lease-v1`. It is a record-bound envelope, **not a bearer credential**. Every route independently requires current Account/app-device/Pro credentials. The server row binds Account/device, exact immutable envelope/request, credential/app/Pro verifier digest, credential expiry, lease revision and per-device monotonically advancing fence. The envelope includes member/owner/credential/runtime generations, Authority generation/epochs/pointer, dataset/op/digest/expected revision and reauthorization provenance. No secret is copied into a pin, local receipt or token.

Fixture `operation_fence_revision` starts with an explicitly known positive integer. Issuance CAS-increments only that Account device; later issuance invalidates older live fences. Repeating an operation cannot renew or extend its lease. Unknown/null/overflow fence, unknown clock/floor, changed request or missing owner proof rejects without repair. `last_owner_now` is a positive, typed, bounded SQL fact; observed expiry is terminal and clock rollback cannot revive it. TTL defaults to10s, max30s, capped by the actual credential expiry. Client wall time never grants validity.

## Transaction boundaries / linearization

1. **Lease issue SQL batch:** authenticate current owner, validate dataset CAS/no existing operation lease, CAS the device fence, insert immutable envelope/token, final joint Account/Pro/writer/fence/expiry assertion. Rollback cannot publish an unproven token.
2. **Dataset SQL commit:** existing repository `applyOperation`, operation UUID/digest/CAS, `sync_records` + `sync_changes` receipt binding and lease consumption are inside the same existing batch. The final **single SQL assertion step** jointly verifies current Account lifecycle/expiry/generations, Pro/writer fence, exact dataset result and consumed current lease. This is the owner/data authorization point. It does not promise expiry validity at physical disk flush time or at a later IndexedDB commit.
3. **Local Authority transaction:** only an opaque scoped `control:apply-owner-operation` capability and distinct attestation can apply the **same already committed** BPM result. Exact base/head/pointer/Control/fence identity, operation/fingerprint/receipt, active readonly birth, unresolved same-generation reservations/journals and ordinary BPM/field/reference checks are revalidated within the existing Authority transaction. Records, manifest, head, typed owner-operation reservation and oplog commit atomically. `suspended=true` and `fenceRevoked=true` remain unchanged. Identity invalidation, independent stop, stale pointer/head/epochs, foreign pending intent or wrong scope rejects. Ordinary `commit`, `resume`, publication and Pro policies retain their guards. Replay requires historical reconciliation; it cannot reapply the receipt.
4. Account DB, Authority DB, Shared backup DB and backend SQL are **separate transactions**. Web Locks serialize cooperating clients, not malicious raw writers. Current Account/source/full manifest/backup and authenticated joint owner-current checks bracket SQL/local calls. They do not create cross-DB atomicity.

## Explicit partial outcomes and limits

The backend knows the **bound pointer value**, not the live pointer in a browser's IDB. A pointer/Account/stop/pending change during an in-flight request may therefore occur after local checks but before SQL success. The backend may commit the originally authorized operation; local pointer/Control CAS then refuses its application. Return `backend-committed-local-unproven`, retain the exact receipt and immutable pins, and stop. Never call this full-save success or automatically replay/apply it. Complete server rejection of every later local pointer change would require owner-coordinated pointer-publication/fence invalidation; that is not implemented here.

A remote revocation after the SQL authorization point cannot erase a valid historical commit. Local materialization is the same committed operation, never permission for a new save. There is no atomic remote-expiry-through-IDB guarantee. Account/backup changes in the last independent-DB window can produce a locally applied historical result with current-state confirmation failed; return `operation-applied-current-unconfirmed`, keep both proven receipts and stop. No successful Admission clears an unrelated stop or transfers an old pending operation into the new generation.

`backendCommitted` and `localCommitted` are separate proven facts (`true` only after validated result); `null` means unproven, not failed or safe to retry. Unknown SQL response, exception, timeout or lost ack cannot imply success. A later read-only `recover({operationId})` can prove exact historical backend/local receipts; it never sends save, creates a new grant, applies missing local data, deletes backup or repairs a floor. Missing/corrupt/mismatched receipt remains unproven. Proven SQL success survives later local/checkpoint failures.

Public `stopReason` is a fixed allowlist (explicit operation required; account changed; Authority pointer/control changed; pending backup unresolved; owner generation changed; credential expired/revoked/unverified; lease/fence unproven; Pro/writer denied; CAS conflict; backend/local outcome unproven; reconcile required). Unauthenticated/ambiguous owner responses remain conservative owner-admission-unproven. No raw error/SQL/credential is echoed as a public reason; exact revocation cannot be inferred when authentication itself is unverifiable.

Same-origin raw IDB writers are not cryptographically excluded; API brands/hashes are not a JS sandbox. Production owner operation routes/schema, coordinated backend/consumer cutover and server fence invalidation, real backup/binary/Cloud restoration, physical crash durability and deployment remain unprovided. Normal B uses its own Account/device/fence/dataset/receipt; delayed revoked A cannot consume or mutate B's credentials, prepared operation or receipt.
