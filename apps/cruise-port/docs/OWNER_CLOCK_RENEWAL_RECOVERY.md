## Owner and transaction map

Reuse existing Account sca1 HMAC, Account/device/member rows, SQL CAS/lifecycle ledger, Port repository/change receipt, Pro/writer fence, Account source inventory, local Authority and Shared immutable backup owner. No new Account DB, settings copy, authentication engine or Sync engine. Proposed fields live on the existing Account device row in disposable fixtures only. Product Worker routers and browser boot never import this capability.

Backend SQL is one owner. Browser Account DB, Authority DB and Shared backup DB are distinct owners. No cross-DB atomicity is assumed. Local credential adoption still requires the existing Account CAS/stop intent/mutation receipt contract and is not implemented here. Explicit backend requests may use a recovered token in memory for isolated tests; they never update normal Account storage.

## Clock / expiry decision

| Candidate | Guarantee and cost | Decision |
|---|---|---|
| Durable per-device monotonic floor | MAX of already durable floor, authenticated SQL observation and current SQL time; one restrictive row update, serializable across instances | Adopted; no global clock service or browser timestamp |
| Durable credential terminal expired/revoked state | Confirmed expired cannot return to active through time rollback; binds verifier/version/lease so old observations cannot expire a newer credential | Adopted with existing lifecycle fields; revoke remains authoritative |
| Atomic auth-fact update + history gate | One UPDATE RETURNING persists floor/expiry and selects only the authorized receipt in the same SQL step | Adopted for current-history/recovery reads; normal saved data stays readonly |
| Memory/localStorage maximum or wall time alone | Lost on reopen, inconsistent across instances or rollback | Rejected as authority |
| Strong globally monotonic time / physical commit deadline | Requires additional production owner/platform guarantees | Not supplied or inferred; remains an operational gate |

`observeOwnerClock` accepts only a HMAC-verified owner SQL snapshot. Its observed timestamp is obtained from the SQL SELECT, not a request field. That observation is included in MAX even if the clock rolls back during HMAC awaits. Unknown floor/lease is rejected, not repaired; complete unissued enrollment retains its narrowly defined NULL-floor initialization exception. Exact credential ID/verifier/version constrain the restrictive update. An old credential's observation cannot overwrite another Account or newer credential.

Current-history preflight records restrictive facts; the final authorized read is an **UPDATE RETURNING on one device row**. It atomically advances floor, marks active/renewing credentials expired when due, and returns the matching receipt only while current permission, identity/generation/member/device binding and expiry hold. A denied or missing receipt can still commit an authorization-only floor/expired fact. No Port record, dataset revision, change receipt, local Account, local Authority or backup is modified by history. This is **domain-data readonly, with explicit owner-authorization writes**, not all-DB readonly. If the write/result cannot be proven, return unproven and no receipt.

SQLite guarantees stable `now` within a sqlite3_step; UPDATE RETURNING changes occur in its first step. References: [date/time functions](https://www.sqlite.org/lang_datefunc.html), [RETURNING](https://www.sqlite.org/lang_returning.html). The receipt subquery reads sync_changes, not a self-referential updated-row subquery. The final statement is the authorization linearization point, not later physical fsync or HTTP delivery. Local workerd/D1 tests verify the actual UPDATE RETURNING behavior.

Once a durable owner expiry observation has committed, rollback/reopen/concurrent instances cannot restore that credential. Save and current-history consult the same terminal state/floor. **An expiry encountered only inside an aborted Save assertion, followed by process loss or clock rollback before a restrictive owner fact can be persisted, is an unknown denial, not confirmed durable expiry.** That operation stays unproven and is not automatically replayed. This patch does not claim to recover an unrecorded SQL timestamp or guarantee absolute UTC expiry under arbitrary unobserved clock faults. A stronger production clock/crash policy is still needed before describing every failed assertion as terminal expiry. No historical receipt supplies current save permission.

## Recoverable renewal

The existing finish-renew endpoint optionally accepts two dedicated headers: `X-Sound-Cruise-Renewal-Recovery` (client CSPRNG256-bit secret) and `X-Sound-Cruise-Renewal-Digest` (exact canonical digest). The new client always supplies both. Legacy headerless renewal retains PR #18 behavior: rotation may succeed, but ACK loss has no new recovery guarantee and remains fail-closed. Client JSON cannot enable the factory's recovery capability.

Digest binds finish request, operation UUID, Account/device/member identity and recovery commitment. Existing request also pins Account/member/runtime generations, transition UUID, old credential version and lease. In the **same existing renewal CAS transaction**, new verifier/version/lease, lifecycle ledger and private recovery envelope/deadline are committed. No result is successful until exact readback. SQL abort rolls back secret rotation, envelope and result together. Different digest, key or operation cannot consume/reissue the result. A repeated finish is never used for recovery.

The envelope contains exact identity/generations, old/new verifier/version/lease, operation/digest/commitment and AES-GCM ciphertext of the already-generated token. HKDF-SHA256 derives an operation-domain key from the random recovery secret; the full binding is authenticated AAD, with fresh96-bit IV. No key or raw token is persisted in SQL. The general receipt contains only public operation/result metadata. The explicit credential response is no-store, never a URL/log field. WebCrypto uses existing platform primitives: [Cloudflare Web Crypto](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/).

Recovery deadline is owner SQL time +30seconds, bounded by the new credential's60second fixture expiry. No lookup extends it. A subsequent begin/rotation/revoke, owner/member change or current-credential mismatch invalidates the prior recovery even if ciphertext is retained. A new recoverable rotation replaces the previous bounded envelope; malformed existing envelope is not silently repaired. No production deletion/retention job is added. Server retention/cleanup and production TTLs remain owner policy decisions.

## Dedicated renewal reconcile

POST `credential/renew/reconcile`: exact operationId/requestDigest, old Bearer credential **plus** the matching recovery secret. Old token alone is never sufficient. It is not accepted by normal Save/current-history authentication after rotation. The dedicated verifier uses the stored old verifier only for this operation proof, then requires the current new verifier/version/lease, exact ledger result, Account/device/member/runtime generations, history/lifecycle permissions, active lifecycle and recovery deadline in owner SQL.

Two authorization-only UPDATE RETURNING checks surround decrypt: before reading the result and after asynchronous decrypt/HMAC validation. Revoke/rotation/generation change before the final check prevents secret delivery. Invalid ciphertext, key, AAD, missing receipt/record, unknown floor, expiry, wrong Account/device or digest returns generic unproven without a credential. Response loss leaves existing proof intact. Same operation/digest may retrieve **the exact same already-issued token**, bounded by current authorization and TTL; it never generates a new token, revision or extended expiry. This is bounded idempotent result delivery, not a one-use claim or an ordinary save receipt.

The same final-read vs physical-response limitation applies. If an owner rotates/revokes after a valid final read, the delivered token may already be invalid; every subsequent use is reauthorized by the owner. It must never be adopted as current solely because of a historical receipt.

## Client durable proof / source pin

`createIsolatedRenewalRecoveryClient` requires the existing Authority fixture scope and matching IndexedDB. Before finish, it generates a random secret and nonextractable AES-GCM CryptoKey. It stores the key, encrypted secret, IV, request/identity/digest and full Account-source digest **in one immutable existing Shared backup owner record**. The key is not in plaintext logs/URLs/general receipts; secret is not stored plaintext. Readback decrypts and verifies the exact digest before any renewal mutation is sent. Key/cipher/metadata are saved atomically; creation-race retry only applies to an immutable metadata add not yet issued. Failure/quota/key loss means no finish, no fallback or overwrite.

The source pin uses the official `createIsolatedAccountCutoverSource` full manifest (supported physical schema3), together with the Account mutation store's opaque context. Opaque contexts are never inspected for nonexistent manifest fields. Both sources are checked around awaits. Reopen requires the exact full manifest digest: same identity with changed revision/fence, ABA, unknown pending state or Account B cannot retrieve/adopt old A's result. Vault/AAD includes the request and source digest; different operation pins never overwrite each other. Client results are historical and adoptionRequired; no automatic Account write or consumer cutover occurs.

CryptoKey nonextractability is not protection against a same-origin script using the key. Same-origin raw writer/script compromise remains an explicit limitation. Browser storage eviction/key loss can make recovery impossible; preserve pending data and use formal owner recovery, never regenerate a credential. Client immutable pins are retained without automatic cleanup or Cloud upload; production retention/export/eviction policy requires separate review.
